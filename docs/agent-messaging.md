# jvo内蔵のエージェント間通信（0.2.0）

**agmsg・Orca・Herdrはインストールも起動も必要ありません。** それらに接続する機能ではなく、jvo自身がタスク担当間の質問、返答、配送判断、永続化、セッション継続を行います。

## 動き

```text
API担当（Codex）: UI担当へ、仕様について質問を提出
  → Jevが配送を承認
  → UI担当（Claude等）が自分の役割・根拠から回答
  → Jevが返答の配送を承認
  → API担当の元モデル・元session・元worktreeへ返答だけを追記
  → 実装を継続し、通常のテスト・独立レビュー・Jev承認へ
```

通信する文章はworkerが生成します。Jevは配送先・配送の可否・回答担当のモデル・元セッションでの続行を選びます。会話で合意しても作業範囲や合格条件は変わらず、完了承認は別の検証経路です。

## 現行実装の範囲

0.2.0は **同じrunの具体的な作業タスク間で、ターンの区切りに会話する方式** です。実装workerが質問を含めた構造化報告を出して待機します。全員が実行枠を保持して相手を待ち続ける設計ではなく、質問待ちの担当は枠を解放し、互いに返答待ちの場合も読取専用の回答ターンを進められます。

相手が既に実装sessionを持っている場合は、そのモデル/sessionで読取専用の回答を行います。相手が未着手の場合は、Jevが許可されたモデルを選び、その担当の仕様と固定snapshotを読む回答ターンを作成します。回答のために依存先の実装を勝手に開始したり、相手の作業場を編集したりしません。

実行中の生成へリアルタイムに文字を注入する機能、別の端末で手動起動済みの任意sessionを自動で取り込む機能、ネットワーク越しの標準 **A2A Protocol** は含みません。これらがなくても、jvo内の異種CLIは質問と返答を交換できます。

## 使い方

`jvo setup` または `jvo models` で許可モデルを設定します。新規設定ではnative messagingが有効になります。旧runでは `--refresh-policy` で承認済みの設定を取り込んでください。

普段はタスクを入力するだけです。Jevが複数の作業タスクを採用すると、workerの指示に宛先一覧と通信方法を追加します。相談が不要なタスクに強制的に会話を付けません。

TUIの `/messages` で質問・返答・宛先・配送状態・snapshotを表示します。終了済みの記録は `jvo messages <run-id>` で読取専用表示できます。オフライン表示はAPIやworkerを起動しません。TUIは本文の表示量を制限し、全本文はSQLiteとcontent-addressed artifactへ保持します。

状態は `proposed`（Jev待ち）、`queued`（配送待ち）、`submitted`（入力したが完了未確認）、`answered`（返答を保存）、`closed`（元担当の継続ターン完了）、`rejected`、`unknown` を区別します。modelが内面的に理解したかどうかは観測できないため、「既読」や「理解済み」という架空の確認は表示しません。

## workerの契約

実装workerはチェックポイントの最終JSONに次を追加できます。

```json
{"summary":"仕様確認のため一時停止します","claims":[],"questions":[],"peerQuestions":[{"id":"Q1","to":"T1-UI","body":"期限切れ応答は401でよいですか。仕様書では…"}]}
```

宛先はjvoが提示したtask IDに限定します。送信者やrun IDはworkerに決めさせず、観測した実行IDから確定します。返信workerは、指定された質問IDを `replyTo` とした `peerReplies` を返します。jvoの管理用IPCやDBをworkerに直接操作させません。

質問・返答とも、Jevの具体的な候補選択とoutboxに結び付けます。通常タスクの無関係な進捗で配送判断を無効にせず、関係するtaskの版、質問元snapshot、policy、scope、本文hash、期限を検証します。配送直前には対象worktreeも再確認します。

## 上限・障害・独立性

一チェックポイント最大4質問、一タスク最大4回の質問チェックポイント、run全体64メッセージ（質問と返答を別々に計上）、既定TTL30分です。通常のworker起動数・Jev呼出し数・経過時間の上限も適用します。会話のための継続は修正試行数へ加算しませんが、worker起動数と使用量には加算します。

複数の質問を提出した場合は、全返答が配送可能になるまで元の実装を再開しません。相手の質問に回答することはその間も可能です。失敗・期限切れ・範囲変更では停止して表示し、Jevに架空の返答を作らせません。

送信中のcrashなどで結果不明の場合は `unknown` を保存します。`jvo recover --acknowledge` で実際のプロセス・ファイルを確認した後、曖昧な会話を破棄した記録を残し、古い質問を自動再送しません。利用者が追加要件や新しい設定を承認した場合も古い会話を退役させます。内容を変えないpause/resumeだけでは会話を失効させません。

回答担当の読取専用状態を前後のfingerprintで確認し、変更があった場合は返答を採用しません。これは事後検出であり、信頼済みローカルCLIをOSレベルで完全に閉じ込めるsandboxではありません。独立レビューsessionへ実装会話全体を共有する経路は作っていません。

## キャッシュ・コスト

元の実装sessionと作業場を維持し、回答だけを追記します。全員へ全履歴を配信したり、司令塔が会話を毎回書き直したりしません。一方で質問の採否と回答にはJev/workerの推論が必要です。読取専用の回答ターンではtoolsetが変わる場合もあり、キャッシュヒットや費用削減を保証しません。

## 実行試験

`test/messaging.test.ts` は、CodexとClaude形式のテスト用CLIを実際の子プロセスで起動し、双方向質問→Jev選択→返答→元session/cwd/modelの継続→テスト→独立レビュー→統合を実行します。実行枠1と3の双方で検証します。送信者偽装、scope/期限、部分返答、配送拒否、読取専用違反、不明配送の復旧も検証します。

推論はfixtureです。実ログイン済みの2社CLIと本番Jev APIによる動作成功や品質・コスト改善率を測定した、という意味ではありません。
