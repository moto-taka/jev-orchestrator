# 必要な判断だけJevへ渡す（0.3.0）

新規runの既定は `lean-v1` です。Jevは方針、モデル・役割、例外、意味上の合否を決めます。決まった作業を続けるためだけの再承認は行いません。実行・権限・予算・状態の鮮度を検査するコードと、実測テスト・独立レビューは残します。

## 何が変わるか

| 場所 | 0.3.0の動作 |
|---|---|
| 通常のtoken・tool進捗 | 従来通り保存・表示のみ。Jevも追加の司令塔も呼ばない |
| A2Aの質問・返答の配送 | 送信元、宛先、本文hash、期限、scope、snapshotを通常コードで確認して配送 |
| 担当済み相手の回答・質問元の続行 | 元のモデル/session/cwdを維持し、通常コードで起動。未割当の相手のモデル選択だけJev |
| 単純なテストassertion失敗 | 許可済みの回数・時間・範囲内で、同じ実装担当へ差分修正。環境障害・原因不明・反復失敗は別途Jevへ |
| 必要なレビューの反復 | Jevが選んだレビューモデルを再利用。ただし会話は実装とも前回レビューとも別の独立session |
| 合否 | 証拠十分性・要件達成・未解決指摘の評価から直接承認。合格を再びChoiceで聞き直さない |
| 合格後の統合 | 合格した固定成果物の通常処理。競合したら専用タスクを作って再検証・再レビュー |
| 単一タスクの最終確認 | 下記の厳しい同一性条件を満たす場合に限り、独立レビューとJevの判定を再利用。最終テストは再実行 |
| 文脈の一次選別 | ローカルで順位付け・サイズ制限。毎回「READMEを読むか」をJevに質問しない |
| 指摘の完全重複 | 同じsnapshot/要件/根拠/再現条件/重大度の完全一致だけを機械的に注記。原文と異なる指摘は保持 |

この変更は「workerが自分で完了承認できる」ことを意味しません。通常コードによる継続処理も、元になった実際のJev判断、許可された操作、scope、実行前条件を記録します。

## 行動の不確実性と、モデル選択の拮抗を分ける

以前は「実装×モデルA」「実装×モデルB」「調査×モデルA」等を一つのChoiceに並べていました。現在は行動と各行動に適任なモデルの質問を分け、同一の根拠を使う独立質問として一回で評価します。各行動のモデル回答は、その行動が選ばれた場合だけ採用します。

難易度の各軸も初回の独立質問として同送します。後の質問が前の回答を見たと仮定していません。モデルが多数同程度に適任であることだけを理由にrunを停止しません。合否や危険な行動の閾値は下げません。モデルは利用者の許可リスト内でのみ選択します。

## 判定の再利用と、通常処理の監査

`decisions` は実際にJevへ問い合わせた記録だけです。通常コードがJev風の確率や承認を偽造することはありません。通常処理はoutboxの `policy` に、rule、元の `decisionId`、関連するtask/scope版、候補hash、判断材料のartifactを持ちます。トランザクションで記録し、実行直前にも検査します。

`/why` はこの二種類を区別します。`jvo metrics <run-id>` は `decisionCalls`、`runtimeTransitions`、`reusedVerdicts` と実測可能なtoken統計を返します。通常の実行処理にかかった件数を、削減した実API料金と換算して表示しません。

## 単一タスクの最終確認を再利用できる条件

最初の依頼をそのまま扱う一つの変更タスクで、計画分割、追加の利用者指示、依存taskがなく、承認済みsnapshotを基準commitからfast-forwardできる場合に限ります。実装・統合のcommit、要件、許可設定、テスト・レビュー対象、指摘、証拠hashが一致し、元の承認が有効であることも確認します。

**commit一致だけで外部DB等の検証環境まで同じとはみなしません。最後のruntimeテストは再実行します。** テスト失敗や統合場の変更があればreadyになりません。複数task、merge commit、競合、scope変更では通常の全体検証・独立レビュー・Jev判定を残します。

## memoに不要な変動を混ぜない

Jevのstateから、単に毎回変化する残りAPI回数・worker起動数を外しました。ルーティングでは必要な予算の可否だけを渡し、上限到達時は実行候補も制限します。実行直前の厳密な予算・権限検査は省略しません。

合否評価には、全許可モデルの一覧や無関係な設定を毎回送りません。違うsnapshotや更新された証拠に合格を使い回しません。providerのprompt cacheとは別の仕組みです。APIモデルのaliasやpolicyが変わる場合の再利用制約も維持しています。

## 旧runの扱い

0.2.0で開始したrunは、勝手に新しい継続権限へ変えず、保存済みの旧動作を維持します。新しいrunはそのままleanになります。保存済みrunを移行する場合だけ実行します。

```sh
# 既存TUIで /pause → /exit を実行した後
jvo resume <run-id> --refresh-policy
```

設定の再確認により、古いテスト・レビューと継続用の権限は再評価対象になります。作業ファイルは削除しません。モデルの許可リストは `jvo models` で変更できます。

## 検証と数字の意味

同じテスト用provider・workerを使った小さな直接実装タスクで、旧制御はJev評価9回、新制御は3回でした。新制御の3回は、初回の方針・実装モデル選択、レビューモデル選択、意味上の合否です。元の隔離デモも、assertion失敗の修正を一回含めて3回で終了します。

これは **制御コードをテスト用入出力で通した経路の測定** です。実Jev APIの速度・課金、実workerの正解率、token削減率、実運用のキャッシュ率を測ったものではありません。複雑な依頼には調査、計画、再判定が追加されます。全taskが3回になるという保証ではありません。

`test/lean.test.ts` ではモデル候補の拮抗、memoの適用条件、実行待ち中のscope変更、完全一致しない指摘の保持、同一commitでも最後のテストが失敗した場合の拒否を確認します。従来の障害・排他・復旧テストも残しています。
